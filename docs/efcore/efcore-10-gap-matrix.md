# EF Core 10 Feature Gap Matrix

Updated 2026-11-23. This matrix corresponds to the [55 feature groups](efcore-10-feature-matrix.md) and tracks only code capability gaps,
explicitly unsupported features, dependencies, and capabilities to confirm. Pre-release tests, acceptance coverage, and review evidence belong only in the [release checklist](efcore-10-release-checklist.md).

Maintenance 10.0.1 migrates CON-01 to Connector 0.5.0; see the [feature matrix](efcore-10-feature-matrix.md).
This dependency migration adds no gap records and changes no existing closure conditions.
Connector 0.4.0 references below identify the original capability baseline; patch acceptance
belongs to the [release checklist](efcore-10-release-checklist.md).

## Statuses and counts

- The fixed statuses are `Not started` / `In development` / `Implemented` / `Blocked` / `Deferred` / `Unsupported` / `To confirm`.
  Update the existing row during development. Once implemented, retain its ID, set it to Implemented, and record the implementation entry point/commit; do not create a separate feature document.
- `P0/P1 completion` identifies feature development to prioritize. `Extension` identifies signatures/metadata capabilities confirmed to be unavailable; it does not automatically add a commitment for the current release.
  `Unsupported` is an explicit rejection in the current contract; update the scope and approach before lifting it. `Deferred` preserves the original release decision for four groups.
- Count G entries as **gap records**: one record may cover a set of overloads. This is not an API count and must not be subtracted from the 55 feature groups.
  G-21/G-28 are related details of deferred groups, not two additional deferred feature groups. Count B/C/D separately; do not present them as Provider development backlog counts.
- The current known unavailable/rejected capabilities are based on the code and package README. Supporting every BCL method is not an implicit Provider commitment.
  Add newly discovered valid requirements to their owning row or give them a new stable ID. Rejection of invalid inputs or malformed models/catalogs is validation, not a missing feature.

Current counts: 50 G records (0 Not started, 0 In development, 30 Implemented, 1 Blocked, 19 Unsupported, 0 Deferred). The inventory also retains 2 Implemented F records, 11 dependency records (B-01 through B-10 and C-03, with 7 Implemented, 3 Blocked and 1 Unsupported), 2 Implemented and 1 Unsupported capability investigations, and 4 Deferred D groups.

## Current integration boundary

Connector 0.4.0 integration implements B-10 scalar Oracle JSON, B-01..04 numeric/parameter
contracts and the supported G-36/C-03/Oracle D-06 reverse-engineering profiles. Expression index SQL,
identity generation/options and standalone sequence cache/order survive generated C#, relational
models and DDL through the annotations documented in the package README. The Provider consumes
public Connector APIs from the published package. MySQL declaration-start catalog integration, other index
kinds and the existing server limitations retain their explicit boundaries. Select further work by the
individual rows below; implemented rows are not an outstanding task queue. Preserve precision, NULL,
converter, ownership and intentional rejection contracts when expanding scope. Final-package, live,
specification and platform acceptance belongs only in the release checklist.

with reliable schema/sequence identity. An additional catalog field or schema-qualified helper would be
optional convenience, not a prerequisite or an existing API. Never substitute advancing `LAST_NUMBER`.
The observed `DBA_OB_DATABASES` projection lacks `DATABASE_ID`, so a name-only join is insufficient.
Closure requires same-name sequences in different databases, exact numeric bounds, sync/async and
cancellation, absence/permission errors, cache/restart behavior and discovery that consumes no values.
Probe results, static Connector/J comparison and release exclusions belong in the release checklist.
